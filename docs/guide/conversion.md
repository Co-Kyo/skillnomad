# 转化手册：把 markdown skill 转化为 skillnomad 管道

> 适用：已通过[四判据自测](quickstart)（≥2 条命中）的长流程管道型 skill。
> 本手册从 sp-skill（案例一）与 narrative-focus（案例二）两次转化中提炼，六步走完即得到一个可构建、可校验的 skillnomad 管道。执行中偏离本手册处，请回写修订（手册与案例互为验收）。

## 六步法总览

| 步 | 名称 | 产出 |
|---|---|---|
| 1 | 痛点盘点 | 痛点清单（现在手写维护到底痛在哪） |
| 2 | 四判据自测 | 命中结论（≥2 条才继续） |
| 3 | 实体建模 | 中间产物命名 → 实体声明 |
| 4 | 链序声明 | steps + dependsOn 单链 |
| 5 | 调度与派生接管 | schedulingPolicy + 派生字段确认 |
| 6 | 验收对照 | before/after 逐段核对，语义无漂移 |

## 步骤 1 · 痛点盘点

列出当前 markdown skill 的真实漂移痛点，每条给出"发生过的事故"或"可预见的漂移方向"。没有具体痛点的项不列入。

- 案例：sp-skill 的痛点是顺序漂移、编号两套体系、路径硬编码（后来全部被机制接管）。
- 空痛点的 skill 不需要 skillnomad——没有痛，转化只是搬家。

## 步骤 2 · 四判据自测

1. 步骤间有真实链序吗（上一步产物 = 下一步输入）？
2. 有可命名的中间产物吗（报告/标注/计划文件）？
3. 有并行/分批/顺序约束吗？
4. 有可推导字段吗（下一步/编号/覆盖状态/校验结果）？

命中 ≥2 条 → 继续。命中不足 → 本手册到此为止，参见[应用面评估的边界](#)（主动讲不适合谁）。

## 步骤 3 · 实体建模

把步骤 2 盘出的中间产物逐个命名，声明为实体（`entities`）：名称、路径模板、类别、描述。实体是全仓唯一事实源——后续步骤引用符号名，不写路径。

- 案例：sp-skill 声明 27 条实体（计划文件/标注结果/检测报告/能力图谱…），步骤层零路径字面量。
- 技巧：先写"这份产物叫什么、活在哪"，再考虑它被谁读、被谁写。

## 步骤 4 · 链序声明

每个步骤一个声明单元：`id`/`title`/`description`/`body` + `reads`（引用实体符号名）/`writes`（产出实体）/`graph`（执行内容）。

**硬约束（构建期报错，先知道少踩坑）**：

- 步骤之间用 `dependsOn` 连成**单链**——两个根步骤即报 `chain is broken`，断链即报 `disconnected`。
- `graph` 是**构造字段**（`task({...})` 的返回值），不是链式方法；旧链式 `.reads().writes().build()` 已不存在。
- 每步需要 `description` + `body`（校验必填）。
- `task` 从 `skillnomad` 主包导入（主包 re-export 全部类型，单包单源）。
- 构建命令需要 tsx 加载器：`npx tsx node_modules/skillnomad/dist/bin/cli.js build <config>`（裸 `npx skillnomad build` 会报 ERR_MODULE_NOT_FOUND）。
- **装配路径二选一并写死**：`createSkillFromModel(模型对象)` 会把 `checkpoint` 转换为 barrier；`createSkill(对象字面量)` 直装配**不转换**——需要用户检查点就用前者。

## 步骤 5 · 调度与派生接管

- 步骤间有并行/分批/窗口需求 → 声明 `schedulingPolicy`（skill 级一等公民）。没有就**留空**——空声明合法（机制可留空是框架弹性）。
- 步骤内有分支/多模式 → 用步骤内 `branch`/`map`/`seq` 表达（顶层是线性链，并行只在步骤内 flow 里）。
- 下一步/编号/覆盖状态等字段 → 确认它们由框架派生（`deriveChainNext`/编号/区间），从你的声明里删掉手写版本。

## 步骤 6 · 验收对照

构建通过后，做一次 before/after 对照收尾：原 markdown 与产物 SKILL.md 逐段核对（模式/检查点/角色标签等结构在位，语义无漂移）。发现漂移回到对应步骤修正后重新构建。

转化记录与产物的留存方式（入库/分支/归档）由你的工作流决定。
