# 转化手册：把 markdown skill 转化为 skillnomad 管道

> 适用：已通过[自测判据](quickstart)（≥2 条命中）的长流程管道型 skill。
> 本手册从 scenario-pipeline 的转化与后续演进中提炼，六步走完即得到一个可构建、可校验的 skillnomad 管道。执行中偏离本手册处，请回写修订（手册与实践互为验收）。

## 六步法总览

| 步 | 名称 | 产出 |
|---|---|---|
| 1 | 痛点盘点 | 痛点清单（现在手写维护到底痛在哪） |
| 2 | 判据自测 | 命中结论（≥2 条才继续） |
| 3 | 实体建模 | 中间产物命名 → 实体声明 |
| 4 | 链序声明 | steps + dependsOn 单链 |
| 5 | 角色与派生接管 | contracts 角色声明 + 派生字段确认 |
| 6 | 验收对照 | before/after 逐段核对，语义无漂移 |

## 步骤 1 · 痛点盘点

列出当前 markdown skill 的真实漂移痛点，每条给出"发生过的事故"或"可预见的漂移方向"。没有具体痛点的项不列入。

- 案例：scenario-pipeline 的痛点是顺序漂移、编号两套体系、路径硬编码（后来全部被机制接管）。
- 空痛点的 skill 不需要 skillnomad——没有痛，转化只是搬家。

## 步骤 2 · 判据自测

1. 步骤间有真实链序吗（上一步产物 = 下一步输入）？
2. 有可命名的中间产物吗（报告/标注/计划文件）？
3. 有并行/分批/顺序约束吗？
4. 有可推导字段吗（下一步/编号/覆盖状态/校验结果）？

命中 ≥2 条 → 继续。命中不足 → 本手册到此为止，[快速上手：不适合的场景](quickstart#不适合的场景)。

## 步骤 3 · 实体建模

把步骤 2 盘出的中间产物逐个命名，声明为实体（`entities`）：名称、路径模板、类别、描述。实体是全仓唯一事实源——后续步骤引用符号名，不写路径。

- 案例：scenario-pipeline 声明 27 条实体（计划文件/标注结果/检测报告/能力图谱…），步骤层零路径字面量。
- 技巧：先写"这份产物叫什么、活在哪"，再考虑它被谁读、被谁写。

## 步骤 4 · 链序声明

每个步骤一个声明单元：`step(id, title)` 链式写 `target`／`summary`／`action`／`reads`／`writes`，`.build()` 收尾。

**硬约束（构建期报错，先知道少踩坑）**：

- 步骤之间用 `.dependsOn()` 连成**单链**——两个根步骤即报 `chain is broken`，断链即报 `disconnected`。
- 每步须有动作正文、检查点（`.checkpoint()`）与至少一条 `writes`——对齐报告逐步核查，缺一项即构建失败。
- 步骤内并行／分支用 `.parallel()`／`.map()`／`.branch()`／`.loop()`；顶层步骤是线性链，可并行的动作不要拆成多个顶层步骤。
- 装配走 `createSkillFromModel(模型对象)`（唯一装配入口）——步骤与 meta／contracts／policies 一起进模型，产物由框架渲染。
- 构建命令（与 starter 模板同款）：`npx tsx node_modules/skillnomad/dist/bin/cli.js build <config>`——`skill.ts` 里的 `.js` 说明符（TypeScript 标准写法）由 tsx 解析回 `.ts` 源。Node ≥ 22.18 也可裸跑 `npx skillnomad build <config>`（原生类型剥离），但说明符须写 `.ts`，两种口径别混用。

## 步骤 5 · 角色与派生接管

- 随包分发的文件逐个进 `contracts` 注册表，声明**角色**（`scope: 'skill'` 或 `scope: 'step'` ＋ 归属步）——发布路径由框架派生（`steps/<NN>-<id>/`、`references/`、`assets/`），见[发布布局](concepts/publish-layout)。
- 步骤内有分支/多模式 → 用步骤内 `.branch()`／`.map()`／`.seq()` 表达（顶层是线性链，框架零调度：并行/分批不在声明层，只在步骤内 flow 里）。
- 下一步/编号/覆盖状态等字段 → 确认它们由框架派生（下一步/编号/区间），从你的声明里删掉手写版本。

## 步骤 6 · 验收对照

构建通过后，做一次 before/after 对照收尾：原 markdown 与产物 SKILL.md 逐段核对（模式/检查点/角色标签等结构在位，语义无漂移）。发现漂移回到对应步骤修正后重新构建。

转化记录与产物的留存方式（入库/分支/归档）由你的工作流决定。
