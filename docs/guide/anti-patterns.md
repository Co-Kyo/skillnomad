# 顶层引导：反模式与「应该怎么做」

> 声明事实，框架推导其余。以下反模式全部来自 skillnomad 自己踩过的坑（9.3 教训清单），
> 写在这里是引导你**别走回头路**。

## 反模式清单

| 反模式 | 为什么不行 | 应该怎么做 |
| :--- | :--- | :--- |
| ❌ 步骤里**手写产物路径**（`{workDir}/xxx.json`）| 8.16 实体投射后路径是业务顶层的派生物——手写即双列表，改一处漏一处 | ✅ 用**产物实体 + 概念引用**（`refOf('ladder').path`），路径只存在于 `entities.ts` |
| ❌ 共用规则用**路径引用**（`assets/common/xxx.md`）| 8.5 的「钢琴缝」——markdown 没有模块化能力，这是硬凑 | ✅ 注册为**内容模块**，步骤用符号名引用（`reads: modules.substitutionTest`）|
| ❌ 步骤**跨步引用**另一个步骤的**私有模块** | 8.15 私有可见性——step 级模块是步骤私有资产，跨步引用会被构建期校验拦截 | ✅ 共享规则声明为 **skill 级模块**；私有规则留在步骤内 |
| ❌ 步骤里**硬编码调度参数**（并发数/窗口）| 8.13/8.14 调度策略是 skill 级一等公民——步骤各自登记会漂移 | ✅ 在 `meta.schedulingPolicy` 声明全局口径，flow 内只表达结构 |
| ❌ **手写顺序/编号/next** | 8.4 起顺序唯一事实是 `dependsOn`（单值）——手写 `next`/序号是第二副本 | ✅ 只声明 `dependsOn`，顺序、编号、区间、总览全部派生 |
| ❌ **手写阶段区间**（`(04-06)`）| phases 只声明「包含哪些步骤」，区间是派生值 | ✅ 只声明 `phases: [{ name, stepIds }]`，区间由框架推导 |

## 三条使用规则（公开承诺）

1. **不要把可并行的动作拆成多个顶层步骤**——顶层步骤之间是线性链（不可并行）；需要并行就在一步内部用 `.parallel()` / `.map()`。
2. **`.dependsOn()` 只传一个前驱**——类型层面就保证「写两个不可能」，另一个方向由框架推导。
3. **派生值不手写**——`next`、序号、区间、flowOverview、调度、路径，全部由框架从声明推导；显式覆盖即自己承担漂移风险。
