# 为什么需要 skillnomad

一句话：**AI 负责写得出来，我们负责活得下去。**

AI 一句话就能生成一个 skill，完全支持你继续这么做——skillnomad 不和 AI 抢生成。它接的是生成之后的半场：当 skill 需要持续迭代时，怎么保证它改得动、改不错、改得轻。

## 先说不适合谁

skillnomad 不是给所有 skill 准备的。以下情况不需要它：

- **一两百字的小 skill**——一屏读完，改起来一目了然，上框架是杀鸡用牛刀
- **一次性 / 用完即弃的 skill**——没有「第 N 次改动」，就没有维护问题
- **单人短流程、很少迭代的 skill**——没有持续演进，管理收益归零
- **只要 AI 生成、从不回头看的 skill**——我们不预言它一定会出问题

**什么时候值得考虑迁移**（满足任何一条再往下看）：

- 改动时开始心里没底——不知道改这一处会影响什么
- 文件数、字符量持续增长——多个 process 互相引用，靠人脑记不下
- 多轮迭代后想自己介入——发现没有任何工具告诉你改得对不对

## 案例对照：sp-skill 的 Before / After（实测）

![案例对照：sp-skill 官方示例的两种形态实测](/svg/case-comparison.svg)

这是**我们团队自己的 skill**（11 步长流程，目前唯一的完整案例），不是第三方用户故事：

- **还是 plaintext 时**：14.7 万字符、最大单文件 8,506、0 测试、序号引用全内联、成环断链靠人眼
- **代码化之后**：流程骨架 -38%、最大单文件 -64%、0 → 8 个测试文件、序号引用全派生、48 次演进可回溯（main 口径）
- **AI 视角不变**：skillnomad 打包后，AI 拿到的 markdown 对齐（本例 diff 为零）——机制藏在幕后，不进 AI 的上下文

::: warning 诚实边界
- 「在本例中，代码化是让它重新可被管理的路径」——是否适用于你的 skill，取决于它会不会走到改动困境那一步
- 「不会悄悄坏」「每处改动都验证过」指**契约内规则**；契约外行为与手写一致
- 数字口径：release vs main 实测（2026-09-02，wc -m，worktree 对比可复现）
:::

## 对「AI 一句话就能写 skill，谁还上代码？」的回应

先承认：对大多数 skill，这个质疑成立。然后说明我们接的是哪一段：

- **一句话写的小 skill，确实不需要 skillnomad**——就像便签不需要版本管理
- **AI 确实能写**——skillnomad 的来源仓恰恰也是 AI 写的；我们不和 AI 竞争
- **「直接就能用」是真的**——第一天能用，之后也许一直够用；我们只服务确实走到改动困境的那部分
- **生成的 skill 一旦长大，改动会变难**——上下文放不下、影响面算不清、错了没人发现（本例的经验：8,506 字的 process）
- 软件业的经验是一个**参照**，不是预言：答案通常不是「不写代码」，是「管理代码」——你的 skill 未必走到这一步
