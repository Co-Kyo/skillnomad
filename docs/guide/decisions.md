# 设计裁定与不走的路

> 写给想知道"为什么是这样设计"的你。skillnomad 的每个边界都记在这里：一句话裁定、它防住的具体事故、以及什么条件下我们会重新考虑。只追加，不改写——推翻一条裁定时，旧条目保留并标注被取代。

## 一条写作路径

**裁定**：作者面只有一条路——`step()` 链式 ＋ `createSkillFromModel` 装配。框架曾同时提供底层 IR 构造子（`task`/`seq`/`parallel`…）作为第二条路，现已退出公开面（内部与测试仍用）。

**防住的事故**：两次真实转化（scenario-pipeline 与第二个移植案例）里，所有作者自发选了链式写法；IR 面只剩框架自己用。两条路没有带来第二种人，只带来第二份要维护的语义与两套要互相翻译的文档。

**重新考虑的触发条件**：出现真实消费者以链式表达不了、而 IR 能自然表达的场景。

## 步骤之间是链，不是图

**裁定**：顶层步骤是一条线性链（`.dependsOn()` 单值），框架不接受 DAG。

**防住的事故**：skill 的产物形态本来就是"00、01、02…按序执行的步骤文件"——用能表达图的结构承载一条链，中间的图能力对产物没有任何价值，属能力过剩；反而让"阶段是连续区间"这类派生失去全序前提。代价也记下了：**无法表达两个顶层步骤同时进行**，确有此需求只能合并为一个步骤在内部并行——没有第三条路。

**重新考虑的触发条件**：出现真实 skill 需要顶层步骤并行且合并为一个步骤会显著损害可读性。

## 框架零调度

**裁定**：框架不承载调度策略——没有 `schedulingPolicy`，并发数/窗口/分批不在声明层。并行只在步骤内 flow（`.parallel()` / `.map()`）表达结构，运行口径归消费者自己。

**防住的事故**：调度声明曾是一等公民，但检查后发现它渲染出的内容消费者都在自己的散文里另写一份——声明层与内容层两套口径必然漂移。删除执行前设了验收门：全仓零调度字样、产物 diff 仅限调度章节消失、其余逐字节不变；消费侧把并发口径收编为自己的常量，两处引用同一来源。

**重新考虑的触发条件**：出现两个以上消费者需要同一种调度派生（即调度口径本身成为可派生的事实）。

## 单包

**裁定**：一个包承载全部公开能力。曾有 types/common/validate 三个子包，已并入主包停止发版；连 `packages/` 目录层级也压平了——合包后那层目录里只剩一个包，层级本身成了谎言。

**防住的事故**：多包时代"装哪个、从哪导入、版本怎么对齐"三问无文档不可答；内部三包版本号必须人工保持同版，正是要消灭的那类派生值。

**重新考虑的触发条件**：无。包的边界按能力划，不按仓库目录划。

## 不承载概念引用形态

**裁定**：`SourceRef.path` 必填；路径解析（概念名→路径）归用户侧 helper（`refOf` 模式），框架不做领域模型抽象。框架曾提供 `ref` 声明形态＋领域 resolver 钩子，已清退。

**防住的事故**：该形态自提供起零真实用例——两次真实转化都自发选择了用户侧 helper 达成同一不变量（步骤层零路径字面量）。原定"由第二用例验证"的路径被真实转化绕开而非采用，这就是答案。

**重新考虑的触发条件**：出现需要框架介入解析、且用户侧 helper 无法自然表达的场景。

## 派生值不手写

**裁定**：`next`、序号、区间、流程总览、发布路径全部由框架从声明推导；显式覆盖合法，但覆盖后框架不再校验其一致性。链不成立时派生函数**返回空而不猜测**——宁可报错，不臆造一个顺序。

**防住的事故**：手写副本是漂移之源——改一处漏一处，两套编号体系并存过、路径硬编码散落全仓过，全部被这条原则接管。

**重新考虑的触发条件**：无——这是总原则，其余裁定都是它的推论。

## 不预做引擎

**裁定**：先声明式，再谈引擎。模块注册表、校验器、发布布局都是"数据＋查表"，不做策略引擎、不做插件市场、不做 DSL。新能力进框架前先回答："为什么不能是一个内容包？"

**防住的事故**：能力过剩即噪音——引擎化的抽象在没有第二个消费者之前只是猜测的形状。抽象的通用性要第二用例实证才认。

**重新考虑的触发条件**：同一模式在两个真实消费者身上重复出现，且声明式表达开始产生复制粘贴。

## 不走的路（外部反例）

- **不做改名吞并**：工具（methodblocks / markrefs）保留独立名字与版本线。反例：Docker Swarm Classic——独立名字与版本线一终止，第三方可用性随之消失。
- **不做业务语义理解**：框架只认结构，不认"扫描""评估"的含义（[核心契约](contract)的"不承诺"节）。
