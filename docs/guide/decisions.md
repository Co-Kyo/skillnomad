# 为什么是这些限制

> **写给谁**：被某条规则顶到、想知道"凭什么"的人。每条一个你的问题、一句结论、一句代价——以及什么情况下这条会松动。

## 为什么顶层步骤不能并行？

顶层步骤是一条线性链（`.dependsOn()` 单值）。skill 的产物本来就是"00、01、02…按序执行的步骤文件"——用能表达依赖图的结构承载一条链，图能力对产物没有价值，反而让"阶段是连续区间"这类派生失去前提。

代价：两个顶层步骤同时进行的场景表达不了，只能合并为一个步骤、在步骤内部并行。当有真实 skill 证明"合并会严重损害可读性"时，这条会重开。

## 为什么每步必须有检查点？

构建要求每步有动作正文、检查点（`.checkpoint()`）与至少一条产出。检查点是执行 AI 停下来问人的地方——长流程最怕的不是慢，是悄悄跑偏一百步之后你才发现。

这是交付质量线，不是可选项。若出现"纯机械步骤加检查点纯属噪音"的普遍场景，会考虑分级要求。

## 为什么框架不管并发数、窗口、分批？

框架零调度：这些不在声明层。步骤内的并行结构用 `.parallel()` / `.map()` 表达，运行口径（并发几个、批次多大）归你——它们几乎总是和你的内容绑定的，写进框架声明层，你就会在自己的提示词里再写一份，两份口径必然漂移。

当多个消费者需要同一种调度派生时，它会作为可派生事实回到框架。

## 为什么概念名→路径的解析要我自己写？

`SourceRef.path` 必填。框架曾提供"概念引用"声明形态加解析钩子，两次真实转化中没有一个作者用它——大家都自发写了几行自己的 `refOf` helper，效果相同且更贴业务。框架不承载没有真实用例的抽象形态。

出现"用户侧 helper 无法自然表达"的场景时重议。

## 为什么写作路径只有一条？

`step()` 链式 ＋ `createSkillFromModel` 装配，没有第二种写法。框架早期附带过一套底层构造子，实践中只有框架自己用——两条路没有带来第二种人，只带来两套要互相翻译的文档。学一次就够。

链式表达不了、底层能自然表达的场景出现时重议。

## 为什么序号、区间、路径都不让手写？

凡是能从声明算出来的（下一步、编号、阶段区间、发布路径），手写就是第二副本——改一处漏一处。链不成立时派生函数返回空并报错，不猜测顺序：宁可停下，不臆造。

显式覆盖合法，但覆盖之后框架不再校验一致性——漂移风险归你。

## 框架为什么不新增业务能力？

skillnomad 保持小而正交：组合、校验、渲染。新业务能力请做成内容包（`packages/`，声明式，不需要可执行入口）。框架里长出来的业务能力，对每个消费者都是强加的依赖。
