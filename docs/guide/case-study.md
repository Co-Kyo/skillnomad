# 案例交代：scenario-pipeline 如何用 skillnomad 建起来

> **写给谁**：想知道"范式在真实长管线里到底改变了什么"的人——不宣传，只交代。本页每个断言附复算方式；做不到的、修过的，如实写在对应位置。

scenario-pipeline（下称 SP）是我们团队自己的 11 步知识管线 skill，也是目前唯一完整走过"plaintext → 范式"全程的案例。2026-09 我们对本页内容做过两轮审查：第一轮取证＋证伪（每个结论跑命令验证，攻击不倒的才留下）；第二轮**产物散文审计**——对发布出来的 markdown 本身做通顺度与可执行性检查，抓出了真实退化（见第四节）。以下就是两轮审查后存活并修复完毕的部分。

## 一、源码怎么建起来的

SP 源码分三面（按读者时刻组织，不按技术分层）：

```text
src/
├── steps/<NN>-<id>/step.ts      # 11 份步骤声明：链式骨架（实测 0% 散文，92-96% 声明）
├── steps/<id>/content.ts        # 该步的散文正本（提示词、判据）——与骨架物理分离
├── packages/<name>/             # 5 个内容包：skill.json 清单＋blocks 散文块（跨步共享的方法论）
├── artifacts.ts                 # 路径单源：所有资产/产物路径只写这一处
├── skill-decl.ts                # 向框架声明：contracts 注册表、模块挂接、策略
└── skill.ts → createSkillFromModel → npx skillnomad build
```

框架拿到的每一句承诺都是**数据**：`dependsOn` 链、`phases` 阶段、`.checkpoint()` 检查点、`scope` 角色——构建期校验（断链/成环/跨步私有/发布布局）拿这些数据查表报错，而不是读散文。路径同步点从迁移前的 4-7 处字面量收敛到 `artifacts.ts` 一处，且资产表↔登记表由测试锁成一一对应。

**诚实限定**：清晰是**声明层**的清晰。散文本身搬进了 `content.ts`——对陌生读者，读 TS 里的散文不比读 markdown 里的散文快；首次了解"某步做什么"，最快的仍是编译产物 `steps/<NN>-<id>/step.md`（一步一份）。范式的优势面在**维护与演化**：改东西时，影响面是机器可查的。

## 二、每一步如何被单独评估

这是范式最实际的改变。我们实跑过一条最小评估回路（以 evaluate-pool 步为例）：

```bash
# 1. 只取该步散文（内容包一行装载；或读该步产物 step.md）
npx tsx -e "import {loadPackage} from 'skillnomad';
  console.log(loadPackage('./src/packages/evaluate').body)" > /tmp/prose.md
# 2. 改一个词（仅 1 个源发点）→ 重建
npm run build
# 3. 全产物逐文件比对：15 个文件里唯一内容变化 = 06-evaluate-pool/step.md 的一行
```

全程 4 条命令、约 1 分钟；未改源连跑两次构建，11 份 step.md 逐字节相同——**diff 干净不是运气，是可重放**。三个步骤（纯 task 步、parallel 步、含包步）各跑过一遍，改动落点均只在本步。

机器还会替你抓住三件事（对照手工拆分文件的旧形态，这三件是净贡献）：

1. **失同步即红**：改阈值表一个值，回归锁精准抓红并指名该步；旧形态里同一评分制在两个文件各写一份、互相矛盾了 20 天没人发现，靠人肉收口。
2. **边界强制**：把 A 步的私有模块塞给 B 步引用——构建失败，诊断直接给出两个步名；旧形态里任何文件可以被任何步骤随手引用，无门可拦。
3. **发布门**：产物里出现源码形态路径、包内引用断链——组装校验拦下。

## 三、数字与复算

对照口径：**发布产物 vs 发布产物**（双侧同为纯 markdown，排除 README）：

| | Before（v1.2.0 产物树，2026-08-30） | After（v1.5.2 范式产物，2026-09-19） |
|---|---|---|
| 文件数 | 50 | 31（-38%） |
| 总字符 | 146,723 | 117,563（-20%） |
| 测试 | 0 | 19 个测试文件（115 测＋产物侧 10 测） |
| 锚点 | commit `79d96aa`（已 bundle 固化） | 本仓 `v1.5.2` tag |

复算方式：Before 侧从固化 bundle 检出后 `git ls-tree -r b1 --name-only | grep '\.md$' | xargs -I{} git show b1:{} | wc -m`；After 侧在当前发布分支同法。旧流传数字「最大单文件 8,506」经查为字符数与行数混算（真值 8,145），已弃用；「产物逐字对齐」的说法经查不成立（内容差异来自 skill 演进），本页不采用。v1.5.2 的回填使产物字符比 v1.5.1 微增 197——把被指针化抹掉的动作写回正文就是要花字数，这个成本我们付（见第四节）。

## 四、我们修过的账：产物散文审计（2026-09-19）

对发布产物做过一次全量散文审计（三路取证＋双证伪），结论先说：**框架一度在产物里制造了质量问题，我们全部认账并修复**。发现与处置：

| 问题 | 归因 | 处置 |
| :--- | :--- | :--- |
| 示例数据被叠加标注（`metrics（示例）: 命题（示例）=10`） | 框架渲染器无条件拼前后缀 | 框架 v0.2.2：行级标注撤除，语义由区块题注一处承载 |
| 构建过程话术泄入执行体（"（D35）""manifest 锁定"） | 框架渲染器注入 | 框架 v0.2.2：中性化，内部编号不进发布物 |
| 插件行印"条件性加载"（声明里根本没有条件） | 框架替作者宣称语义 | 框架 v0.2.2：撤除假断言 |
| 任务正文被"见模块附录"指针化，域绑定动作断供 | 作者为迁就内容包单源改坏内容 | SP v1.5.2：域绑定动作全部回填正文（level_weight/anchor_ref/related/material），通用方法论留包 |
| 跳过条件正文与正本两说（按一方可跳过、按另一方不可） | 消费仓双源漂移 | SP v1.5.2：统一＋双源一致锁 |
| 参数表退役后 `url-batch-size` 悬空引用 | 删档未回填 | SP v1.5.2：值内联（实况核对：四值中仅此一个真断链，其余系死参数，不造需求） |

这些缺陷在 115＋110 个测试全绿下漏网——原因不掩饰：**既有测试只断言"数据进没进文本、结构缺没缺"，从不读文本本身**。所以修复之外立了门：框架提供 `scanMetaDiscourse`（元话语黑名单）与 `scanMarkerDuplication`（标记叠加）两把通用扫描器，消费仓接线域绑定词存活锁、参数守恒、双源一致共 5 道产物侧门（`verify:product`，CI 在构建后执行）——散文质量现在是机器校验的承诺，不是姿态。
