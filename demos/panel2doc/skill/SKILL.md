# panel2doc：角色面板讨论 → 决策文档

分两步走：先让三个角色吵一轮，再由主持人收口；然后把收口的结果写成标准格式的决策文档。
不要跳过第一步直接写文档，那样出来的东西没有反对意见，一看就是拍的。

## 第一步：三方角色讨论

1. 明确议题。本 skill 默认议题是「内部 CLI 工具该不该从 HTTP 接口迁到 gRPC」。如果用户给了别的议题，用用户的，但角色仍然固定是下面三个，不换。

2. 起 3 个 subagent，一个角色一个，各自独立跑，不要把别人的观点先告诉它——提前知道就没有真正的分歧了。每个 subagent 的 prompt 里写清楚：它扮演谁、议题是什么、必须交回哪三样东西。

3. 三个角色固定为：

   - 资深后端工程师：关心性能和运维成本。流式、多路复用、代码生成、连接治理是它的语言；也会算 CI/CD、网关、监控、客户端升级这些账。
   - 产品经理：关心交付速度和用户感知。它的判断标准是"用户多久能拿到""学习成本有没有变""会不会拖掉这个季度的活"。
   - 安全审查者：关心认证、审计和暴露面。mTLS、token 轮转、审计日志能不能落到一条链上、proto 一变暴露面变没变，是它的问题。

4. 每个角色必须交付这三样，缺一样就让它补：

   - 立场：迁 / 不迁 / 有条件迁（只能选一个，不许"视情况而定"这种滑头话）。
   - 三条理由，每条一两句话，要能落到具体事情上，别写"提升可维护性"这种空话。
   - 一个让对方让步的条件：说清楚"如果谁能满足 X，我就改立场"。这个字段最有用，后面的分歧表主要靠它。

5. 三个角色都回来后，你当主持人，做一张分歧表。四列：议题点 / 谁和谁分歧 / 分歧的实质是什么 / 现状（已共识 或 仍分歧）。

   分歧的实质要往下挖一层。比如后端说"gRPC 性能更好"、产品说"用户感觉不到"，实质不是性能数字，是"这个收益有没有人来验收"。把这一层写出来。

   已经共识的条目也要列出来，别只写吵的部分——共识是决策文档里"依据"的来源。

6. 主持人不下结论，只整理。这一步结束时的产物是：三份立场 + 一张分歧表。

## 第二步：写成决策文档

1. 打开 references/report-standard.md，那是四段标准格式和每一段的写法要求。整份文档严格按那四段来，顺序也别调。

2. 内容全部从第一步的产物里取，不要自己新观点：

   - 结论看多数立场和有条件迁的那几个条件；
   - 依据逐条标来源角色，标成（后端）（产品）（安全）这种；
   - 风险这一节里，反对意见最强的一条必须原样保留，不许弱化、不许合并掉；
   - 待决直接从"让对方让步的条件"和仍分歧的行里翻译过来——谁定、什么时候定、定什么。

3. 写完后自查三件事：四段齐不齐；依据每一条是不是都能追到某个角色的原话；最有力的反对意见在不在。少一样就补，别交。

4. 输出 markdown，文件名带上议题和日期，放在用户指定的位置；用户没说就放在当前目录，并在回复里告诉他放在了哪。

## 两个提醒

角色的人数不要加减。三个是刻意选的：再加一个"测试负责人"之类的，讨论会散掉，两两分歧也变成一堆混战，主持人收不了口。

如果三个角色意见完全一致，那大概率是 prompt 写漏了、它们串了观点。重跑第一步，别硬出一份没有风险的文档。
